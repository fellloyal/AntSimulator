# 食物块大小逻辑修复 - 2026-06-05

## 背景

用户反馈：在放置食物过程中，在原来的小的食物上继续放置有时候会变成更大的食物，逻辑有问题。

## 根因分析

当前 NxN 块大小扫描存在两个 bug：

### Bug 1：blockSize 扫描方向错误

**MapEditor.tsx 252 行**：
```ts
foodCellMap.has((y + blockSize) * gridW + x)  // 检查 (x, y+blockSize)
```
这是**同列下方扫描**，不是 NxN 方块检查。对于一个 2x4 的纵向食物区，会错误地认为 blockSize=4。

**FoodPileRenderer.ts 85 行**：
```ts
foodMap.get((y + blockSize) * world.map.width + (x + blockSize))  // 检查 (x+blockSize, y+blockSize)
```
这是**对角线扫描**，也不是 NxN 方块检查。对于两个相邻的 2x2 块（位置 (0,0) 和 (2,2)），会错误认为 blockSize=3。

### Bug 2：锚点逻辑漏掉相邻块

当前用"上方或左方无同类型食物"判断锚点。对于两个相邻的 2x2 块：
- 第一个块：左上 (0,0) 是锚点 ✓
- 第二个块：左上 (0,2) 的上方 (0,1) 是食物，所以不是锚点 ✗

**第二个块永远不会被绘制**。

## 复现案例

用 `foodBlockSize=2`（小）：

1. 在 (0,0) 放置 2x2 → 显示小图 ✓
2. 在 (0,2) 放置 2x2 → 旧逻辑：扫描 (0,1)、(0,2)、(0,3) 都是食物，blockSize=4，画一个 4x4 大图 ✗

新逻辑：第一个 2x2 画小图，第二个 2x2 也画小图 ✓

## 修复方案

**两步重构**：

1. **取消锚点限制**：遍历所有未绘制的食物单元，对每个单元都尝试找最大 NxN 块
2. **正确的 NxN 块扫描**：从 N=1 开始扩展到 N+1 时，必须检查新增的整行和整列都是同类型食物

```ts
let blockSize = 1;
while (x + blockSize < gridW && y + blockSize < gridH) {
  // 检查新行 y+blockSize: x..x+blockSize 全是同类型食物
  let allFood = true;
  for (let bx = 0; bx <= blockSize; bx++) {
    const c = foodCellMap.get((y + blockSize) * gridW + (x + bx));
    if (!c || c[3] !== type) { allFood = false; break; }
  }
  if (!allFood) break;
  // 检查新列 x+blockSize: y..y+blockSize 全是同类型食物
  for (let by = 0; by <= blockSize; by++) {
    const c = foodCellMap.get((y + by) * gridW + (x + blockSize));
    if (!c || c[3] !== type) { allFood = false; break; }
  }
  if (!allFood) break;
  blockSize++;
}
```

## 验证场景

| 场景 | 旧行为 | 新行为 |
|------|------|------|
| 单个 2x2 | 小图 | 小图 ✓ |
| 两个相邻 2x2 | 第一个画 4x4 大图，第二个不画 | 各画一个 2x2 小图 ✓ |
| 重叠放置 (NxN + MxM) | 大图（取决于对齐） | 各画对应的 NxN / MxM 块 ✓ |
| 1xN 纵向条 | 大图 | N 个 1x1 小图（合理退化）✓ |
| L 形 | 部分丢失 | 每个连通区域都正确处理 ✓ |

## 性能

NxN 扫描每步 O(N)，最多 4 步，总 O(N²) 很小；遍历所有未绘制单元，整体 O(单元数 × 4²) = O(单元数)，对编辑器视口（数千格）毫秒级。
