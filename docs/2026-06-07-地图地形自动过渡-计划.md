# 2026-06-07-地图地形自动过渡-计划

## 背景

当前地图编辑器中每种地形（草/沙/水/石头）都是独立的 SVG 瓦片，相邻地形之间是硬边（每个 cell 用同一种底色 + 装饰图案）。问题：

- 草地和沙地突然切换，缺少海岸/岸边的渐变
- 水面和草地之间是硬切，看起来像贴图
- 沙地嵌入草地中间看起来像贴块

参考红色警戒等经典 RTS 地图编辑器：相邻地形之间用一套**过渡瓦片（autotile / blending tiles）**自动拼接，边缘根据上下左右邻居的地形类型自动选择过渡形态。

## 目标

实现"autotile / 边缘过渡"机制，让相邻不同地形之间的边界自动呈现合理的过渡形态，无需手工绘制过渡。

## 方案对比

### 方案 A：预生成 4-bit 邻接过渡瓦片（边掩码，16 种）

**思路**：每种地形的 SVG 瓦片拆成 16 种"邻接组合"——根据该格子的上、下、左、右 4 个邻居分别是否是同类地形（共 2^4 = 16 组合），自动选一张对应过渡图。

- 每种地形 16 张子瓦片，4 种地形 = 64 张
- 边过渡效果不错，但**角点（3 种地形交汇）处理粗糙**

### 方案 B：运行时边缘混合（Canvas API）

**思路**：每个 cell 画完后，检查上下左右 4 个邻居，如果地形不同，就在 cell 边缘画一条**过渡色带**（混合色或半透明叠加）。

- 例如草地格子的下边是沙地 → 在 cell 底部 2-4px 范围内画一条草地→沙地的渐变色
- 优点：无需新资源
- 缺点：仅支持 2 种地形间的平滑过渡，**角点处理困难**（3 种地形交汇无法平滑）

### 方案 C：24-tile autotile（边 + 角，推荐）⭐

**思路**：在 16 种边掩码基础上，**额外叠加 4 个角点的细节**，处理"凸角/凹角"形态。

```
主体：4 边（上/下/左/右）是否与中心同地形 → 2^4 = 16 种
角点：4 角（左上/右上/左下/右下）对角是否同地形 → 2^4 = 16 种
实际渲染：base = edgeMask，4 个角各画一个 8x8 小填充（凸出/凹入）
```

**16 种边掩码不够自然的原因**：
举例：草地的右侧格子是**沙地** vs **水**，16 种掩码对这两种情况都返回 `mask=8`，会画同一张子瓦片，无法区分。

而 24-tile 在角点对角匹配时，单独画一个 8x8 的小填充来体现"凸角"和"凹角"差异：
- 草地右上角是水（角对角是草）→ 草地**凹入**角
- 草地右上角是沙（角对角是水）→ 草地**凸出**角

**资源量**：
- 主体瓦片：16 张/地形
- 角点瓦片：4 张/地形（标准 4 角，可旋转复用）
- 总计：4 × 20 = 80 张

**性能**：
- 仍是 O(N) drawImage，每帧绘制 ~100-300ms（基于 100×100 地图的估算）

### 方案 D：47-tile（红警/WC3 标准）

- 47 张子瓦片（4 边 × 8 角 + 中心 + 4 边 + 4 角）
- 美术资源量翻倍
- 角点处理最精细
- 项目当前规模不需要

## 推荐方案：C（24-tile） ⭐

视觉上明显比纯 16 种自然，角点（3 种地形交汇）能正确处理凸/凹角形态。

**资源按地形对优化**：
- **草↔沙**：全套 16 主体 + 4 角（自然渐变，岸滩）
- **草↔水**：全套 16 + 4 角（重点，海岸线）
- **沙↔水**：全套 16 + 4 角（沙滩入海）
- **草↔岩**：8 种（岩是装饰，不需精细）
- **沙↔岩**：8 种

总资源量：3 × 20 + 2 × 8 = 76 张

## 推荐方案：C + B 混合

- **方案 C（24-tile autotile）** 用于**草↔沙**、**草↔水**、**沙↔水**、**草↔岩**、**沙↔岩**之间的过渡（5 种过渡关系）
- **方案 B（边缘渐变）** 用于**水↔沙**（海岸线）的特殊处理（水边浪花/湿润效果）

具体实施：

### Phase 1：autotile 数据结构

```ts
// 邻接掩码：4 位分别表示 [上, 下, 左, 右] 是否是同类
export type EdgeMask = 0..15; // 0=无同类邻居, 1=上, 2=下, 3=上+下, ...

// 角点掩码：4 位分别表示 [左上, 右上, 左下, 右下] 对角是否同类
export type CornerMask = 0..15;

// 每种地形为每个掩码预生成一张过渡子瓦片
export interface TerrainAutoTiles {
  terrainId: string;
  edgeVariants: Record<EdgeMask, string>; // 16 张主体 SVG
  cornerVariants: Record<'tl' | 'tr' | 'bl' | 'br', string>; // 4 张角点 SVG
}

// 角点查表：[edgeMask][cornerMask] -> 是否画角贴片 + 凸/凹
export interface CornerLookup {
  isConvex: boolean; // true=凸角（向外延伸），false=凹角（向内收）
  tile: 'tl' | 'tr' | 'bl' | 'br';
}
```

**生成策略（程序化生成 SVG）**：

对草地（grass）来说：
- 掩码 0（无同类邻居）：纯草地，但边缘有向外扩展的"草尖"，延伸到邻居格子的 ~2px 范围
- 掩码 1（上邻居是草地）：下边缘保持纯草
- 掩码 2（下邻居是草地）：上边缘保持纯草
- 掩码 3（上+下都是草地）：纯草（无边缘变化）
- 掩码 4（左邻居是草地）：右边缘保持
- 掩码 5（上+左）：右下角扩展草
- 掩码 8（右邻居是草地）：左边缘保持
- 掩码 15（全方向都是草地）：纯草

角点：4 张 8x8 SVG 单独画
- 凸角（角对角是同类，但两边都不是）：向外扩展的"齿"
- 凹角（角对角是异类，且两边都是同类）：向内收的"缺口"

### Phase 2：渲染时计算邻接掩码

```ts
function computeEdgeMask(cell: Cell, neighbors: { up, down, left, right }): EdgeMask {
  let mask = 0;
  if (neighbors.up?.terrain === cell.terrain) mask |= 1;  // bit 0
  if (neighbors.down?.terrain === cell.terrain) mask |= 2; // bit 1
  if (neighbors.left?.terrain === cell.terrain) mask |= 4; // bit 2
  if (neighbors.right?.terrain === cell.terrain) mask |= 8; // bit 3
  return mask;
}

function computeCornerMask(cell: Cell, neighbors: { tl, tr, bl, br }): CornerMask {
  let mask = 0;
  if (neighbors.tl?.terrain === cell.terrain) mask |= 1;  // bit 0
  if (neighbors.tr?.terrain === cell.terrain) mask |= 2; // bit 1
  if (neighbors.bl?.terrain === cell.terrain) mask |= 4; // bit 2
  if (neighbors.br?.terrain === cell.terrain) mask |= 8; // bit 3
  return mask;
}
```

每帧绘制时，按 (terrain, edgeMask) 分桶，每桶按 cornerMask 再分桶，主体批量画 + 角点单独画。

### Phase 3：海岸线特殊处理（水↔沙）

水边叠加一层**湿润沙滩**（沙色 + 蓝色水波混合），在水面格子向上下左右是沙地的边缘画 1-2 像素的浅蓝色湿润带。

实现：在水地形渲染后再扫一遍可见区域，对水边格子额外画一条 "beach_wet_edge" 纹理。

### Phase 4：编辑器实时反馈

地图编辑器中画地形时，每帧重新计算邻接掩码（用 ref 缓存 + 局部失效），保证所见即所得。

## 数据结构

### Cell 扩展

不需要改变 `Cell` 数据结构——地形只存一个 0-3 的整数，邻接关系在渲染时按需计算。

### SVG 资源生成

提供 `scripts/generate-terrain-tiles.mjs` 脚本，根据基本地形 SVG + 邻接规则生成 76 张子瓦片 SVG 字符串，输出到 `src/render/assets/TerrainAutoTiles.ts`。

## 性能评估

- 当前：4 桶 × N cell
- 新：4 地形 × 16 边掩码 × 16 角掩码 = 1024 桶（但实际只有地形边界的格子需要角点处理）
- 实际开销：分桶字典查询 + 角点单独 drawImage，仍在 12ms 帧预算内
- 邻接计算：8 次 map.getByCoords() × N cell，每帧 ~2-3ms（100×100 地图）

## 风险与回退

- **风险 1**：自动生成的子瓦片视觉质量不高 → 保留原始"无过渡"模式作为编辑器开关（默认关闭）
- **风险 2**：地图编辑器中拖动画地形时频繁重算掩码卡顿 → 增量更新：只在 paint/erase 影响的 cell 周围 1 圈重算掩码
- **回退**：保留原 `drawTerrain()` 方法，新方法命名为 `drawAutoTerrain()`，通过 store 开关切换

## 不在本次范围

- 47-tile 全套实现（当前 24-tile 够用）
- 3 种以上地形交汇的角点处理（保持硬切）
- 装饰性元素（树、岩石）在过渡带的摆放
- 季节变化（草地变黄等）
- 地图生成器自动放置地形（目前用户手工编辑）

## 验收标准

- 草地和沙地相邻时，边界自动呈现草尖渐变到沙地的效果，无明显接缝
- 水边草地/沙地时，水面有湿润带效果
- 3 种地形在角点交汇时，能正确区分凸角和凹角形态
- 地图编辑器中拖动画地形时无卡顿（< 1 帧延迟）
- 现有测试场景（纯草地地图）视觉无变化
