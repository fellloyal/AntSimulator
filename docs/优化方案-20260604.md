# 优化方案 - 20260604

> 基于项目现状与 `docs/优化探讨.md` 思路，针对 Web 版本的具体优化方案

## 当前性能瓶颈分析

### 1. 模拟主线程阻塞（最大瓶颈）
- `sim.update(dt)` 在主线程 `requestAnimationFrame` 中执行
- 1000 只蚂蚁时，每帧需处理：位置更新 × N + 标记采样 × N + 战斗检测 × N
- SoldierUpdater.findMarker 每只兵蚁 64 次随机采样，开销极大
- 主线程同时承担模拟计算 + Canvas 渲染，互相抢占

### 2. 标记渲染逐格 fillRect（渲染瓶颈）
- WorldRenderer.render 中标记层对每个可见 cell 调用 `ctx.fillRect()`
- 1920×1080 世界 / cellSize=4 → 480×270 = 129,600 个 cell
- 即使只渲染可见区域，仍可能有数万次 fillRect 调用
- 每次调用还要拼接 `rgb(r,g,b)` 字符串，GC 压力大

### 3. 蚂蚁数组管理低效
- `Colony.removeDeadAnts()` 使用 `Array.filter()` 每次创建新数组
- `Colony.soldiersCount()` 每次遍历全量蚂蚁
- `FightSystem` 中 `getAntById` 线性查找（虽然 O(1) 索引，但 id 可能不一致）

### 4. 战斗系统遍历开销
- `FightSystem.checkForFights` 遍历所有蚁群的所有蚂蚁
- 即使大部分蚂蚁不参与战斗，仍需遍历判断

## 优化方案

### 一、Web Worker 离线模拟（对应优化文档：CPU 多线程并行计算）

**优先级：高 | 预期收益：帧率提升 30-50%**

将 `Simulation.update()` 移入 Web Worker，主线程只负责渲染。

**实现方案：**
1. 将 `simulation/` 目录下的纯逻辑代码移入 Worker
2. 使用 `SharedArrayBuffer` + `Atomics` 或 `Transferable` 传递蚂蚁位置/方向数据
3. 主线程每帧从共享缓冲区读取最新状态进行渲染
4. 数据同步策略：
   - 蚂蚁位置/方向/相位 → Float32Array（每只蚂蚁 8 float：x, y, angle, phase, type, wobble, dyingTimer, isPaused）
   - 世界网格标记 → 另一块 Float32Array（标记强度、食物、墙壁）
   - 双缓冲：Worker 写 back buffer，主线程读 front buffer，每帧交换

**限制：**
- 需要服务器设置 `Cross-Origin-Isolation` 头（`COOP` + `COEP`）才能使用 `SharedArrayBuffer`
- 备选方案：使用 `postMessage` + `Transferable` 传递数据（有拷贝开销但无需特殊头）

### 二、ImageData 批量像素渲染（对应优化文档：批量渲染优化）

**优先级：高 | 预期收益：标记渲染提速 5-10 倍**

将标记层从逐格 `fillRect` 改为 `ImageData` 直接写像素。

**实现方案：**
1. 创建一个离屏 Canvas（尺寸 = 世界网格尺寸）
2. 每帧创建 `ImageData`，直接写入像素 RGBA 值
3. 用 `putImageData` 一次性绘制
4. 蚂蚁层仍然用 Canvas 2D API 绘制（数量少，开销可控）

**伪代码：**
```typescript
const imageData = ctx.createImageData(gridWidth, gridHeight);
const data = imageData.data;
for (let i = 0; i < cells.length; i++) {
  const cell = cells[i];
  const idx = i * 4;
  // 计算 RGBA
  data[idx] = r;
  data[idx + 1] = g;
  data[idx + 2] = b;
  data[idx + 3] = a;
}
ctx.putImageData(imageData, 0, 0);
```

**优化细节：**
- 只在标记有变化时重绘 ImageData（利用已有的 `dirtyCells` 追踪）
- 缩放时用 `ctx.drawImage(offscreenCanvas, ...)` 让浏览器做插值

### 三、兵蚁采样优化（对应优化文档：海量实体批量调度）

**优先级：中 | 预期收益：兵蚁多时帧率提升 20-30%**

当前 `SoldierUpdater.findMarker` 每只兵蚁 64 次随机采样，极其昂贵。

**优化方案：**
1. **减少采样数**：64 → 16（与工蚁的触角采样 + 8 次探索采样对齐）
2. **触角采样**：兵蚁也采用工蚁的双触角采样策略，先快速检测前方左右，再少量随机探索
3. **方向偏好采样**：在当前方向 ±60° 范围内采样，而非 ±126°（PI * 0.7）

### 四、蚂蚁数组优化（对应优化文档：海量实体批量调度）

**优先级：中 | 预期收益：减少 GC 停顿**

**优化方案：**
1. **swap-and-pop 删除**：替代 `Array.filter()`，避免创建新数组
   ```typescript
   removeDeadAnts(): void {
     let writeIdx = 0;
     for (let i = 0; i < this.ants.length; i++) {
       if (!this.ants[i].isDead()) {
         this.ants[writeIdx] = this.ants[i];
         this.ants[writeIdx].id = writeIdx;
         writeIdx++;
       }
     }
     this.ants.length = writeIdx;
   }
   ```
2. **缓存 soldiersCount**：在 `specializeSoldier` / `removeDeadAnts` 时维护计数器，避免每次遍历
3. **预分配蚂蚁池**：用对象池替代 `new Ant()`，减少 GC 压力

### 五、战斗系统空间索引优化（对应优化文档：碰撞检测系统）

**优先级：中 | 预期收益：多蚁群战斗时帧率提升**

**当前实现分析：**
- 已利用网格 `currentAnt` 做空间索引（蚂蚁注册到所在 cell）
- `FightSystem.checkForFight` 通过 cell 的 `markers[otherColony].currentAnt` 查找敌人
- 但 `checkForFightsInColony` 仍遍历所有蚂蚁

**优化方案：**
1. **战斗候选集**：只对 `fightMode === NoFight && type === Soldier` 的蚂蚁检查战斗
2. **空间分区快速查找**：维护一个 `fightingCells` 集合，只检查有敌方蚂蚁注册的 cell
3. **延迟战斗检测**：不需要每帧检查，可以每 3-5 帧检查一次

### 六、信息素轨迹可视化渲染优化（对应优化文档：信息素轨迹可视化渲染）

**优先级：低 | 当前已有基础实现**

**优化方案：**
1. **离屏 Canvas 缓存标记层**：标记变化不频繁时复用上一帧
2. **渐变衰减动画**：利用 ImageData alpha 通道做自然衰减，而非每帧重算
3. **脏区域局部更新**：只重绘 `dirtyCells` 对应的像素区域

## 实施优先级排序

| 顺序 | 优化项 | 预期收益 | 实施复杂度 |
|------|--------|----------|-----------|
| 1 | ImageData 批量像素渲染 | 渲染提速 5-10x | 中 |
| 2 | 兵蚁采样优化 | 兵蚁场景 20-30% | 低 |
| 3 | 蚂蚁数组优化 | 减少 GC 停顿 | 低 |
| 4 | 战斗系统优化 | 多蚁群战斗提速 | 中 |
| 5 | Web Worker 离线模拟 | 帧率 30-50% | 高 |
| 6 | 信息素可视化优化 | 视觉效果提升 | 中 |

> 注：Web Worker 收益最大但复杂度最高，且依赖服务器配置，建议放在后期。
> ImageData 渲染优化收益高且相对独立，建议优先实施。
